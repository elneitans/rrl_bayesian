# H5: integración de BART con fitted Q

Nota de avance: [H6](h6.md) implementa posteriormente el adaptador y piloto
Breakout con extracción visual; este documento conserva el alcance original de H5.

H5 implementa el primer RRTL-B ejecutable usando el kernel grow/prune de H3.
H4 (General BART y change/swap) permanece pendiente y no es una dependencia
para esta integración. La recolección y la reanudación se validaron en un MDP
controlado; el adaptador y el piloto Atari de RRTL-B corresponden a H6.
El baseline y los archivos legacy conservan su comportamiento.

## Componentes

| Archivo | Responsabilidad |
|---|---|
| `bayesian_rrtl/q_config.py` | Configuración completa, acciones ordenadas, semillas y hash |
| `bayesian_rrtl/replay.py` | Replay FIFO acotado, IDs monotónicos y muestra uniforme por acción sin reemplazo |
| `bayesian_rrtl/targets.py` | Targets con un modelo congelado; tratamiento explícito de terminales y truncación |
| `bayesian_rrtl/agent.py` | Ensembles por acción, epsilon-greedy, calibración de ruido, ajustes y evaluación |
| `bayesian_rrtl/checkpoint.py` | Persistencia versionada con checksum y escritura atómica |
| `bayesian_rrtl/training.py` | Recolección, contadores, retornos y estado completo del episodio |
| `bayesian_rrtl/toy_mdp.py` | Entorno relacional pequeño con Q óptimo conocido y snapshot del entorno |
| `train_bayesian.py` | Entrenar, reanudar y evaluar el MDP controlado desde CLI |
| `experiments/validate_h5.py` | Validación reproducible con tres semillas |

El núcleo continúa independiente de Gym/ALE. El agente recibe estados de `Fact`
o filas de `EncodedBatch`, con un encoder fijado antes de recolectar. Una acción
es un índice en `config.actions`; ese orden se mantiene en modelos y checkpoints.
El runner incluido está dedicado a `TwoStepMDP`: no acepta checkpoints Atari.

## Semántica de cada bloque

1. `observe` registra recompensa transformada y original, estado codificado,
   flags terminales, identificadores de episodio/paso y un ID de transición único.
   Epsilon avanza por interacciones, nunca por sweeps.
2. Cada `fit_interval` interacciones se muestrea por acción hasta
   `batch_size_per_action` elementos del replay, sin reemplazo. El replay tiene
   capacidad global: una acción puede quedarse sin datos si sus ejemplos envejecen.
3. Se conserva el modelo anterior y se construyen **todos** los targets antes
   de ajustar la primera acción: `r + gamma * max Q_target(s_next, ·)` cuando
   corresponde bootstrap. Datos y targets quedan congelados durante las cadenas.
4. Se reinicia BART por acción con los priors fijados y nuevo burn-in. No se
   reutilizan draws de datasets anteriores ni se aplica una actualización TD
   incremental adicional a las hojas.
5. Se publican juntos los modelos, RNG, calibraciones y contadores del bloque.
   Si falla un ajuste, esos componentes permanecen en su estado anterior; se
   puede reintentar el ajuste sobre el replay ya recolectado.

Antes del primer ajuste se usa `Q=0`. Una acción sin datos conserva su posterior
anterior; si nunca se ajustó, permanece marcada como no ajustada. Su inicialización
Q=0 no se presenta como una distribución con incertidumbre cero: pedir sus draws
produce un error explícito.

Para terminales reales no se codifica ni consulta el siguiente estado. Para
truncaciones se usa la observación final, con bootstrap configurable. Si hace
falta bootstrap y no existe esa observación, se rechaza la transición antes de
incrementar contadores. Un corte de presupuesto no se transforma en terminal:
el checkpoint conserva el episodio parcial y las transiciones aún no ajustadas.
No se fuerza un ajuste al guardar; así el lugar donde se pausa no cambia el
calendario de fitted Q.

Cada fit conserva `fit_id`, `target_model_id`, hash de configuración, IDs de
transición, hash de datos/targets, cobertura por acción, excesos de escala,
magnitud de Q, diagnósticos MCMC y tiempos. El checkpoint incluye el dataset
completo del último fit y el modelo objetivo usado para generarlo. Los registros
históricos conservan métricas; no acumulan todos los datasets ni draws antiguos.

## Escala y ruido

La escala queda fijada por las cotas de recompensa transformada y `gamma`:
`L=min(0,r_min/(1-gamma))`, `U=max(0,r_max/(1-gamma))`, `c=(L+U)/2`, `W=U-L`.
No se recortan objetivos ni predicciones fuera de las cotas.

Para cada acción, el primer batch no vacío sirve de piloto de entrenamiento para
calibrar `lambda_a` una sola vez. Se usa una regresión auxiliar con intercepto y
codificación one-hot de las categorías observadas, incluyendo faltantes. No se
tratan los códigos categóricos como distancias. Si el diseño no es identificable,
se usa varianza de respuestas; con datos insuficientes o varianza cero se aplica
el piso configurable (`1e-8` por defecto, en unidades normalizadas).

Se persisten escala, `k`, `nu`, `lambda_a`, método de calibración y piso. Esta
calibración temprana es una decisión del MVP y requerirá sensibilidad en el piloto
Atari; no implica que la incertidumbre posterior sea una posterior del MDP.

## Guardado y reanudación

Hay RNG separados para entorno, exploración, replay y MCMC por acción. El
checkpoint `.rrtl` guarda configuración, encoder/hash, modelos actuales y objetivo,
árboles, draws, ruido, replay, contadores, calibraciones, buffer de acciones,
estados RNG y snapshot del recolector/entorno. Valida versión, checksum, hash de
configuración, escala y correspondencia de catálogos. El formato usa pickle y
solo debe cargarse desde archivos locales confiables.

`QTrainingSession` requiere que el adaptador del entorno proporcione:

- `reset(seed=...) -> estado relacional`.
- `step(action) -> (estado siguiente, recompensa transformada, recompensa original, terminated, truncated)`.
- `snapshot()` y `restore(snapshot)` con RNG, contadores y memoria del extractor.
- `close()`.

La reanudación exacta está comprobada con el mismo software y runtime. Un
checkpoint del agente sin snapshot del recolector permite evaluar o continuar
ajustes sobre el replay, pero se rechaza para reanudar un episodio. No se guarda
una cadena MCMC a mitad de sweep: los checkpoints se producen entre interacciones
y ajustes completos. Los tiempos de ejecución naturalmente difieren al reanudar;
las comparaciones exactas corresponden al estado del aprendizaje.

La evaluación usa una copia del agente y entornos nuevos, devuelve recompensa
original y no modifica replay, RNG ni posterior de entrenamiento. Las semillas
de validación/test son disjuntas y se excluyen del generador de semillas de
entrenamiento. La política usa la media latente, sin añadir ruido residual.
El remuestreo opcional de acciones repetidas sigue la convención del baseline.

## Ejecutar

Desde la raíz del repositorio, con las dependencias existentes:

```bash
.venv/bin/python train_bayesian.py \
  --config configs/bayesian_toy.json --output results/h5_toy --steps 600

# 200 interacciones adicionales; conserva intacta la ejecución de origen.
.venv/bin/python train_bayesian.py \
  --resume results/h5_toy/final_checkpoint.rrtl \
  --output results/h5_resumed --steps 200

# Evaluación independiente, sin volver a entrenar.
.venv/bin/python train_bayesian.py \
  --checkpoint results/h5_resumed/final_checkpoint.rrtl --eval-split test

.venv/bin/python -m experiments.validate_h5 --output results/h5_validation_new
.venv/bin/python -m pytest tests/test_fitted_q.py -q
```

Cada entrenamiento requiere un directorio nuevo. `--steps` cuenta interacciones
adicionales incluso al reanudar; el log reanudado conserva también las filas
anteriores. La evaluación predeterminada es `validation`; `test` solo se ejecuta
al pedirlo. Repetir evaluación reemplaza el JSON del split, sin cambiar el
checkpoint ni los registros. El entrenamiento produce `manifest.json`,
`train.csv`, `fits.json`, `summary.json` y `final_checkpoint.rrtl`.

## Evidencia y límites

El MDP tiene dos estados no terminales. En el primero, `advance` lleva al segundo
con recompensa 0 y `exit` termina con 0.4. En el segundo, ambas acciones terminan,
con recompensas 1 y -0.2. Con `gamma=0.8`, la ecuación de Bellman da:

| Estado | Q(advance) | Q(exit) | Acción óptima |
|---|---:|---:|---|
| Inicial | 0.8 | 0.4 | advance |
| Segundo | 1.0 | -0.2 | advance |

Con 600 interacciones, 6 fits y semillas 11, 22 y 33, se recuperaron las dos
acciones óptimas en las tres ejecuciones. El error máximo absoluto de Q fue,
respectivamente, `3.66e-7`, `4.90e-7` y `8.95e-7`.

Se guardó cada ejecución dentro de un episodio, después de 302/303 interacciones,
y se comparó su continuación con una reanudación independiente hasta 600:
transiciones, RNG, targets y draws coincidieron exactamente. Las pruebas añaden
un entorno con ruido y remuestreo de acciones para comprobar también ese estado.
Los resultados están en `docs/validation_h5.json`; los checkpoints de evidencia
están en `results/h5_validation/` (ignorados por Git).

La precisión del MDP determinista no demuestra rendimiento en Atari ni mezcla
adecuada en datasets complejos. H6 debe construir el adaptador Atari, verificar
su manejo de observaciones finales y estado del extractor, medir costo e inferencia
y ejecutar el piloto con baseline pareado. H4 y la campaña H7 siguen pendientes.
